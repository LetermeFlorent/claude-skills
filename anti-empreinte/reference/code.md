# Code, tests and reviews

Code generated by a model is recognised less by its words than by its habits: comments that narrate,
defensive layers nobody asked for, a demo block at the end of the file. Match the files next to the one
you edit. The `clean-code` skill holds the wider rules (file size, one concern per file, no comment,
English names); this page holds what gives a model away.

## What the scan finds in code

`scan.py` reads every code file line by line. A `by hand` row is an AI attribution, chatbot residue or
a placeholder. A `flag` row is typography (em dash, curly quotes, invisible characters, odd spaces) or
an emoji found on a code line: inside a comment it is fixed; inside a string literal it is a value,
since changing it changes what the program prints, so propose the new string and ask. Code you write
yourself never has them in the first place. In page and style files the scan also reports the interface
defaults of `visual.md`.

Placeholders it knows: `// ... existing code ...`, `... rest of the code ...`, `TODO: implement`, an
`Example usage` block, `your_api_key_here`, `replace with your`, `[insert ...]`.

## Habits to drop

Each of these shows up in generated code far more often than in code a person writes.

- A comment that says what the next line does. A comment explains why, or there is none.
- A docstring on a trivial function, an `Args:` / `Returns:` / `Raises:` block by default, the same
  docstring shape on every function of a file.
- Section banners (`# ===== Helpers =====`), `# Step 1:` comments, `# Note:`, `# Helper function to`.
- An import added in case. A parameter nobody passes. A config option nobody sets.
- A broad `try` / `except Exception` that ends on a `print` or swallows the error. Handle the errors
  the code can meet, the way the neighbouring files do.
- Defensive checks on values the type or the caller already guarantees, `isinstance` chains, `None`
  checks on every argument.
- An `if __name__ == "__main__":` demo, an `# Example usage` block, a `main()` that prints sample
  output, in a module that is not a script.
- Emoji or decorated output in the console or the logs of code you write (a check mark before
  "Done!", a rocket before "Starting"), and log lines in full sentences ending on an exclamation mark.
- Your own naming or error handling imposed on a project that has its own.
- Version pins or API calls written from memory: check the version the project uses.
- Generic identifiers in series (`data`, `result`, `temp`, `item`, `helper`, `utils`, `manager`) when
  the domain has a word.

## Tests

Generated tests fail in their own ways.

- A unit test never calls a real API or a real network service: mock the boundary.
- Never invent a rule the tested function does not have, never assert on a value you did not compute
  from the code.
- Keep the project's test naming and layout. No `test_should_..._when_...` names in a project that
  writes `test_total_empty`.
- No test that only checks a mock was called, no test that passes whatever the code does.

## Code review comments

Never write "consider extracting this into a separate function", "for better readability", "this could
improve maintainability", "nit:" by reflex, or praise before the point. Say the concrete problem, the
line, and the fix. One comment per problem, in the reviewer's own voice.

## Files an agent leaves behind

`IMPLEMENTATION_SUMMARY.md`, `CHANGES_SUMMARY.md`, `FIX_NOTES.md`, `REFACTORING_PLAN.md`,
`SESSION_LOG.md`, `repro_*.py`, `scratch_*.js`, `debug_*.sh`: the scan flags them by name. Delete the
ones you created in this task; ask about the others. Plans, notes and reports for the user go in
`.ia/` or the temporary folder, never into the repository.

## Infrastructure as code

HCL or YAML that validates but ignores the real state, the provider versions and the project's
variables is a generated file. Read the existing modules, pin what they pin, reuse their variables.
